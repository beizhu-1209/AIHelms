# AIHelms 平台规则

## 平台定位

AIHelms 是企业 AI 资源管理平台，以 LiteLLM 为底座，通过管理后台（admin）增强管理能力，通过用户端（web）提供资源接入入口。

- **管理后台（admin）**：面向管理员，基于 LiteLLM 的增强管理界面，覆盖模型、Skill、MCP Server、组织、安全等管理场景
- **用户端（hub）**：面向用户，展示可用 AI 资源（模型 key、MCP、Skill），用户获取信息后接入本地客户端，实际连接 LiteLLM

## 核心原则

1. **不修改 LiteLLM 源码** — 只通过 LiteLLM API/配置交互，保证可独立升级
2. **平台数据结构优先** — 数据先写入平台表，再同步到 LiteLLM
3. **平台数据结构是超集** — 包含 LiteLLM 所有字段 + 平台扩展字段
4. **开发前理解 LiteLLM** — 每个模块开发前，必须先了解 LiteLLM 对应板块的原理和数据结构，在此基础上设计

## 数据完整性规则（强制）

以下规则为强制性约束，所有开发必须严格遵守：

### 平台数据库必须是唯一数据源

1. **所有业务数据必须存储在平台数据库中** — 任何功能涉及的数据，无论是否需要同步到 LiteLLM，都必须先在平台 DB 中有完整存储
2. **禁止仅依赖外部系统存储业务数据** — 不允许出现"数据只在 LiteLLM / Redis / JSON 文件中，平台 DB 没有"的情况
3. **外部系统是同步目标，不是数据源** — LiteLLM 是下游消费者，平台 DB 是 source of truth。即使 LiteLLM 数据丢失，平台必须能完整恢复
4. **成本与效能报表只读平台数据** — 成本、预算、效能、看板统计只能读取平台落库后的日志/汇总表及平台计算字段（如 cost_summary_daily、llm_call_logs、mcp_call_logs、ai_keys），禁止直接读取 LiteLLM 原始 spend 作为业务展示或计算口径
5. **禁止用功能逻辑美化脏数据** — 遇到异常成本、脏数据或同步错误时，不得在前端/后端通过过滤、截断、换源、默认值覆盖等方式隐藏问题；应按平台数据原样展示，并单独记录为数据质量问题或治理任务

### 数据结构设计要求

1. **关键字段必须为独立列** — 不允许将核心业务字段（如 model、api_base、tpm、rpm、定价）仅存储在 JSONB 中。JSONB 只用于存储扩展/可选/不确定结构的数据
2. **JSONB 字段中的核心信息必须同时有独立列** — 如果一个 JSONB 字段中的某些 key 是业务逻辑必须读取的，必须提升为独立列
3. **运行时数据由 LiteLLM 产生，平台定时拉取** — usage、spend、logs 等数据由 LiteLLM 在请求过程中产生，平台通过定时任务拉取存入平台 DB 用于分析报表；实时查询场景直接调 LiteLLM API
4. **每个功能模块必须有完整的 DB 表设计** — 新功能开发前，必须先设计并创建对应的数据库表，不允许"先用 JSONB 凑合"

### 数据同步要求

1. **写入流程（业务配置）**：平台 DB 写入成功 → 同步到 LiteLLM → 记录同步状态
2. **读取流程（业务配置）**：优先读平台 DB，LiteLLM 数据仅作为补充或校验
3. **同步失败不影响平台功能** — 如果 LiteLLM 同步失败，平台自身功能不受影响，标记同步状态待重试
4. **同步策略按数据类型区分**：
   - **业务配置数据**（模型、Key、凭证、部署、预算等）→ 实时同步，平台 DB 先写，再推到 LiteLLM
   - **运行时数据**（usage、spend、logs）→ LiteLLM 产生，平台定时拉取存入 DB 用于分析；实时查询直接调 LiteLLM API
   - **不使用 LiteLLM Callback** — 避免挂载自定义文件到 LiteLLM 容器，违反"不修改 LiteLLM"原则

### 禁止事项

- ❌ 禁止新功能只通过 LiteLLM API 存取数据而不建平台表
- ❌ 禁止将不可替代的业务信息仅存在 JSONB 黑盒中
- ❌ 禁止依赖 LiteLLM 的实时 API 作为唯一数据来源（如 /model/info、/key/info）
- ❌ 禁止在没有平台 DB 表的情况下开发 service 和 API 层

## 数据流

```
管理后台 CRUD → 平台数据库 → 同步到 LiteLLM
数据分析 ← LiteLLM usage/log + 平台扩展数据
用户端 → 读取平台数据 → 用户本地客户端 → LiteLLM API
```

## 管理后台模块

### AI身份

- **组织管理**：人员、角色、组织的 CRUD，采用 RBAC 模型
- **AI身份**：为每人分配 AI 身份，一人可持多个 key（一个主 key + 多个场景 key），key 可关联模型、MCP、Skill、成本统计等资源，用户可通过 web 端申请

### 智能体中心

智能体的创建、配置和生命周期管理

### AI市场

- **Skill**：Skill 的发布与上架管理，包括申请使用审批，用户可通过web端申请。
- **MCP**：MCP Server 的发布与上架管理，包括申请使用审批，用户可通过web端申请。

### 模型纳管

- **供应商管理**：AI 模型供应商的接入与配置
- **模型管理**：模型的注册、配置，同步到 LiteLLM

### 数据中心

- **成本中心**：基于 LiteLLM usage + 平台扩展数据的成本分析
- **日志管理**：基于 LiteLLM log + 平台扩展数据的日志查询与分析

### 安全

- **管理员日志**：管理员操作审计记录
- **敏感信息识别**：AI 交互中的敏感信息检测与防护

### AI实验室

- **Caching**：缓存策略配置
- **Policies**：规则策略管理
- **文件处理**：文件相关的 AI 处理能力

## 用户端

用户端是只读展示 + 资源申请入口，不直接管理资源。用户从这里获取接入信息（key、endpoint、MCP 地址等），配置到本地客户端后通过 LiteLLM 使用 AI 服务。
